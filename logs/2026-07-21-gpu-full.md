## Key decisions made this session (also saved to memory)

1. **CUDA stays an optional (weak) dependency**, not hard. Reasoning: FLOWVPM
   is a dependency of FLOWUnsteady/VortexLattice; a hard CUDA dependency
   would force the ~40-package CUDA stack onto every downstream CPU-only
   user and onto HPC/offline installs. Verified empirically that CUDA.jl
   itself installs/precompiles fine even with no GPU present
   (`CUDA.functional() == false`, no error) — the concern is dependency-tree
   weight/blast-radius, not platform support. Checked FastMultipole's actual
   source: its `nearfield_device!` is a generic overload stub
   (`@warn "...hasn't been overloaded by the user"`), i.e. FastMultipole
   itself is designed to stay CUDA-agnostic at the core too — consistent
   with, not contradicting, this choice. (FastMultipole's maintainer hasn't
   finalized their own CUDA-optional-vs-hard decision yet, but the
   optional-for-FLOWVPM choice weakly dominates regardless of what they
   decide — see conversation for the full scenario analysis.)
2. **Package extensions (not `Requires.jl`)** are the mechanism, since that's
   the current Julia-blessed standard (built into the resolver, precompiles
   ahead of time, no world-age quirks) — and the same pattern is intended for
   VortexLattice's future GPU work.
3. **FMM/FastMultipole is not a permanent CPU-only exclusion.** Original plan
   scoped Phase 4 (FMM-GPU) as "deferred until the colleague's FastMultipole
   GPU work lands" — correct, but should be read as sequencing, not a
   permanent wall. Don't hardcode CPU-only assumptions into the FMM path;
   `UJ_fmm` already forwards `nearfield_device=(pfield.useGPU>0)` straight
   through to `fmm.fmm!(...)`, which is correct and should stay as-is. When
   Phase 3 test scaffolding is built, wire FMM+GPU configs in a
   ready-to-enable way rather than writing them as permanently excluded.
4. **CPU/GPU code-sharing standard going forward:** default to one shared
   implementation (broadcasting over row-slices of `pfield.particles`) for
   elementwise per-particle physics (Phase 1's scope: time integration,
   relaxation, viscous, SFS) — this works unchanged for `Matrix` and
   `CuArray`. Fork into two separate implementations only when performance
   genuinely requires it. The O(N²) direct-sum pairwise kernel is the
   accepted precedent for forking (hand-tiled `@cuda` kernel in the
   extension vs. the CPU nested loop in `src/FLOWVPM_fmm.jl`'s
   `fmm.direct!`) — broadcasting can't express that shared-memory tiling
   optimization, so this predates the branch and isn't a design failure.
5. **User will run GPU tests on the supercomputer** once a GPU-only test
   point is reached (no local GPU hardware) — write those test files clearly
   enough to run and interpret standalone.

## Follow-up session (same day): bugs found in the fork's timeintegration rewrite, RK3 vectorized

The fork's `_euler` rewrite (both ClassicVPM and ReformulatedVPM) had a **real,
silent correctness bug**: `G = pfield.particles[GAMMA_INDEX, :]` and similar
row-slice captures use plain bracket-indexing, which in Julia always **copies**
(not a view) when the index is a range/`:` rather than a scalar. Every
subsequent `G[i, :] .+= ...` mutated only that throwaway copy and never wrote
back to `pfield.particles` — i.e. vortex stretching and SFS dissipation were
silently no-ops. Confirmed with a live repro (`vpm._euler` on a 2-particle
field with a nonzero `J`: `Γ` was unchanged before the fix, changed correctly
after). Root cause: `A[range, :]` copies; `view(A, range, :)` (or `@view`)
does not. Fixed by switching every row-slice that gets *mutated in place*
(`J`→read-only stays a copy is fine, `G`/`M`/etc. that are written to) to
`view(...)`.

Also found and fixed a second, independent bug in the ClassicVPM `_euler`'s
SFS-dissipation line: `C_all[1, :] .* SFS_all` broadcasts a `(np,)` vector
against a `(3,np)` matrix along the wrong axis — throws `DimensionMismatch`
for any `np != 3`. This was never caught by CI because the test suite's
`vpm.cVPM` alias is actually `ReformulatedVPM(f=0,g=0)`, not the literal
`ClassicVPM` struct — so the genuine `ClassicVPM{R}()` formulation path (used
via `vpm.formulation_classic`) is currently untested by the existing test
suite and the bug was dormant. Fixed by transposing the offending row vectors
to `(1,np)` before broadcasting (`C_all[1,:]'`, `sigma3'`), matching the style
already used for `active'` elsewhere. Verified directly against literal
`ClassicVPM` formulation (not the `cVPM` alias) after the fix.

**Lesson for the rest of Phase 1 (relaxation/viscous/subfilterscale):** when
vectorizing, always use `view(pfield.particles, ROWS, :)` for any row-slice
that gets written to in place — plain `pfield.particles[ROWS, :]` copies and
silently drops the write. Read-only captures are fine as either. Also
double-check broadcast shapes when mixing a `(np,)` "one value per particle"
vector with a `(k,np)` "k components per particle" slice — needs an explicit
transpose/reshape to `(1,np)`, or it either errors (`k != np`) or silently
computes garbage (`k == np`, coincidentally shaped).

**RK3 vectorized (this session, after user asked to retry rather than leave
it as a loop):** `update_particle_states` for both ClassicVPM and
ReformulatedVPM rewritten as row-slice broadcasts. Key subtlety vs. Euler: `M`
(RK low-storage memory) is *not* purely additive — `M[k] = a*M[k] + dt*(...)`
overwrites, it doesn't accumulate a delta. So the static-particle mask can't
just zero the delta (that would corrupt `M` for a static particle by writing
`0` instead of leaving its previous value alone); it has to *blend*:
`M[k,:] .= ifelse.(isactive, new_value, old_value)`. `X`/`Γ`/`sigma`, which
genuinely are `+=` deltas, use the simpler `active .* delta` masking as before.
Deleted `update_particle_states_multithreaded`/`thread_assignments` (already
done by the fork, confirmed nothing else references them).

**Verification:** full `] test` suite passes (14/14 test sets, including both
Euler and RK3 paths, ClassicVPM/ReformulatedVPM, direct/FMM UJ, viscous,
constant/dynamic SFS). Perf sanity: `rungekutta3` at n=2000 particles with

**Correction to the above: CPU perf regression found, then resolved by forking
into two implementations (not by pure vectorization).** After reporting the
"negligible overhead" line above, the user asked specifically about RK3's
isolated cost (ignoring the O(N²)/FMM N-body time). Isolated benchmark
(`update_particle_states` alone, n=500/2000/20000, `@belapsed`/`@allocated`):

| n | broadcast (initial) | scalar loop | ratio |
|---|---|---|---|
| 500 | 57.0 us | 7.4 us | 7.7x |
| 2000 | 233.3 us | 30.1 us | 7.7x |
| 20000 | 2098.7 us | 315.1 us | 6.7x |

Root cause: each named intermediate (`MM1`, `Gnorm2`, `MM4`, `M1_new`...`M8_new`,
etc. -- ~13-15 of them per call) is a fresh heap-allocated `(np,)` array in the
broadcast version, vs. plain stack-allocated scalars in the loop (0 bytes).
Confirmed the static-particle masking logic was NOT the cause (stripping it
out entirely only dropped allocation by ~3%) -- the intermediates themselves
are the cost. Tried preallocating a persistent scratch buffer
(`pfield.scratch`, a new `AT`-typed field on `ParticleField`, `N_SCRATCH=16`
generic rows, same row-index-range convention as `particles`) and writing
every intermediate in-place via `.=` instead of `=`: this cut allocation
~300x (1.4MB -> ~4.7KB/call) but only closed the speed gap to ~4-4.7x (still
memory-bandwidth-bound: ~20 separate statements each doing a full read/write
pass over all particles, vs. the loop's one-pass-per-particle fusion).
Same regression independently confirmed for `_euler` (Reformulated): 7-10x
slower, up to 10MB/call at n=20000, isolated the same way.

Tried `@turbo` (LoopVectorization.jl) as a possible single-implementation
fix -- benchmarked faster than the plain loop (5.3/17.6/182us vs. loop's
7.4/30.1/315us at n=500/2000/20000, zero allocation) -- but `@turbo` only
compiles against `Array`/`StridedArray`, never `CuArray`, so it can't be the
shared GPU implementation either way; using it would still require a
CPU-only code path. **User decided against adding LoopVectorization as a new
dependency** (deemed the extra dependency+risk not worth it for a CPU-only
speed bump when a zero-dependency fork already gets the win) and instead
directed: **fork into two implementations** -- restore the original
zero-allocation scalar loop, untouched, as the CPU (`Array`-backed) path;
keep the (already-tested-correct) broadcast/view/scratch-buffer version as
the GPU (any non-`Array`-backed) path, selected at runtime via
`pfield.particles isa Array`. This mirrors the precedent already accepted for
the O(N²) direct-sum kernel (Phase 2) -- broadcasting/shared CPU-GPU code was
the *default* per the branch's standing rule, but is explicitly *not*
mandatory when it costs real CPU performance; forking is the accepted
fallback, not a failure.

**IMPORTANT CORRECTION: `] test` never exercises the broadcast/GPU path at
all** -- every test `pfield` is `Matrix`-backed, so `pfield.particles isa
Array` is always true and every test dispatches to the CPU loop. Initially
"verified" the broadcast path only by calling it once and confirming it
didn't error -- this is NOT sufficient (see below, a real bug slipped past
exactly this level of check). The only valid verification for the broadcast
path is a direct numerical diff against the CPU loop on the same input,
done explicitly (construct pfield, deepcopy it, run CPU loop on one copy and
broadcast on the other, compare `pf_loop.particles` vs `pf_bcast.particles`
elementwise) -- added this as a standing requirement, see memory update.

**Scratch buffer size reduction (user request): `N_SCRATCH` 16 -> 11,
uniform for both formulations (explicitly not sized differently per
formulation -- user rejected that option).** Achieved via safe row-aliasing
in `update_particle_states_broadcast_reformulated!`: several scratch
quantities die before others are computed (`MM1/MM2/MM3` dead once consumed
by `M4_new/M5_new/M6_new`; `Gnorm2` dead once `MM4` is computed from it;
`S_dot_G` dead once `MM4` is computed), and since every formula here is
purely elementwise per-particle (output at index i depends only on inputs at
index i), overwriting a dead quantity's own row (`x .= f(x, ...)`) is
well-defined -- same principle as the standard `x .= x .+ 1` pattern.
ClassicVPM's broadcast function (already using few rows) just moved its
`active` row from 16 to 8 to fit the smaller buffer; no aliasing needed
there.

**Real bug found and fixed during this reduction, via the newly-required
direct numerical diff (NOT caught by `] test`, confirming the point
above):** the `MM4`/`Gnorm2` row-alias was split across two broadcast
statements --
```julia
MM4 .= (...) ./ max.(Gnorm2, eps(R))       # writes into Gnorm2's row
MM4 .= ifelse.(Gnorm2 .> zero(R), MM4, 0)  # reads Gnorm2 -- but it's already MM4's value now!
```
The second statement's `Gnorm2` read is stale -- by then the row holds the
first statement's output (the raw MM4 value), not the original squared-norm,
so the `> zero(R)` guard test was comparing the wrong quantity. Aliasing
`Gnorm2`/`MM4` is safe WITHIN one fused broadcast statement (elementwise, all
inputs read before any output written, per Julia's broadcast semantics) but
NOT safe split across two separate statements that both reference the same
row before and after it's overwritten. Fixed by fusing the guard and the
division into one statement: `MM4 .= ifelse.(Gnorm2 .> zero(R), (...) ./
Gnorm2, zero(R))` -- both branches are evaluated for every element
regardless of the condition (`ifelse.` is not short-circuiting), so a
Gnorm2=0 particle transiently computes a NaN/Inf in the discarded branch,
which is harmless (IEEE754 doesn't trap, and `ifelse` just selects the
zero(R) branch's value for that index) -- this matches how the original
scalar loop's `if/else` avoids computing the division at all for that case,
just via a different (branchless) mechanism. Re-verified after the fix:
`max abs diff` between CPU loop and broadcast output is exactly `0.0` for
both formulations, with and without static particles, at n=200.

## Update (2026-07-21, later session): relaxation collapsed to a single shared implementation

User asked whether relaxation could be a single implementation (not
forked CPU-loop/GPU-broadcast) "with minimal cost", given the benchmark
showed only 1.4-2.1x CPU slowdown (much smaller than time integration's
4-10x). Decided the cost was acceptable and collapsed it: all 4 call sites
in `FLOWVPM_timeintegration.jl` (`_euler` x2, `rungekutta3` x2) now
unconditionally call `relax_broadcast!(pfield.relaxation, pfield)` -- the
`pfield.particles isa Array` fork and the per-particle scalar loops
(including the `Threads.@threads`/`MIN_MT_NP` split in `rungekutta3`) are
gone from these call sites. `time integration`'s own physics (`_euler_cpu_*`
vs `_euler_broadcast_*`, `update_particle_states_cpu_*` vs
`update_particle_states_broadcast_*`) is UNCHANGED -- only relaxation was
unified.

**Real hazard caught and fixed, not hypothetical:** collapsing to always call
`relax_broadcast!` meant *every* relaxation scheme -- including a
downstream-defined custom one -- now goes through `_relax_broadcast!`
dispatch. The original fallback method (`_relax_broadcast!(relax, rlxf,
pfield) = nothing`, written to make `norelaxation` a no-op) would have
silently done nothing for any custom relaxation scheme without a registered
broadcast method too -- previously harmless on CPU because the CPU loop
called `rlx.relax` directly, bypassing dispatch entirely. Fixed by: (1) giving
`norelaxation`'s function a name (`relaxation_none_fn` in `FLOWVPM.jl`,
replacing the old anonymous `(args...;optargs...)->nothing`) so it can be
dispatched on specifically, with its own `_relax_broadcast!` no-op method
defined right next to it in `FLOWVPM.jl` (must be file-order-correct:
`FLOWVPM_relaxation.jl` is `include`d before `relaxation_none_fn` exists, so
the method can't live in the relaxation file); (2) changing the generic
fallback in `FLOWVPM_relaxation.jl` to `error(...)` with a message pointing
at exactly what method a custom scheme needs to define. Verified both: the
direct numerical diff (0.0/5.96e-8-noise, same as before) still passes, and
a custom relaxation scheme without a broadcast method throws the intended
error instead of silently doing nothing.

**Public API note (superseded by the revert below, kept for the record):**
this paragraph described a behavior change that only existed while
relaxation was collapsed (see revert immediately below) -- it no longer
applies now that the CPU path is back to calling `rlx.relax` directly via

## Update (2026-07-21, same session): collapse reverted -- back to forked CPU/GPU

After reporting the benchmark, root-caused *why* the gap widened with np
(693ns->1.00us at np=100, 1.4x; 75.5us->160us at np=10,000, 2.1x): the
original scalar loop used `Threads.@threads` once `pfield.np > MIN_MT_NP`
(1000) in `rungekutta3`'s relax block, so at np=10,000 the loop was running
multithreaded while the broadcast is single-threaded -- almost certainly the
dominant term in the growing ratio, not raw broadcast overhead. User chose
to keep CPU threading rather than accept that cost, so the collapse was
reverted: all 4 call sites in `FLOWVPM_timeintegration.jl` (`_euler` x2,
`rungekutta3` x2) are back to forking on `pfield.particles isa Array` ->
original per-particle scalar loop (including the `Threads.@threads`/
`MIN_MT_NP` split in `rungekutta3`) / `else` -> `relax_broadcast!`, exactly
as originally implemented earlier this session.

**Kept from the collapse detour (still correct, not reverted):** the
`_relax_broadcast!` fallback fix. `norelaxation`'s function now has a name
(`relaxation_none_fn` in `FLOWVPM.jl`) with its own explicit no-op
`_relax_broadcast!` method, and the generic fallback for any other
unrecognized relaxation scheme now `error()`s instead of silently doing
nothing. This still matters even with the fork restored: a downstream
custom relaxation scheme used with `useGPU`/`CuArray` would otherwise hit
the broadcast path and silently no-op with no warning.

**Considered but not implemented (proposed as a future optimization, not
done):** re-adding CPU threading to a *broadcast* implementation (chunk
`1:pfield.np` into `Threads.nthreads()` pieces, run the same broadcast
statements over `view(..., chunk)` per thread) as a way to eventually unify
CPU/GPU relaxation without losing threading. Not pursued once the user opted
to just keep the existing fork instead.

  correctness on real hardware.
